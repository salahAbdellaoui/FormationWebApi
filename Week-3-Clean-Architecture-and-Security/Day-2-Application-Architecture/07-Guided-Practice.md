# 07 — Guided Practice

**Duration:** 25 minutes

---

## Objective

Trace the existing Create Employee use case through all layers, explaining each architectural pattern as you encounter it. By the end, you should understand how the pieces fit together and why each pattern exists.

---

## Step 1 — The HTTP Request

The request starts in the controller:

```csharp
[HttpPost]
public async Task<ActionResult<EmployeeDto>> Create([FromBody] CreateEmployeeDto dto)
{
    var created = await _employeeService.CreateEmployeeAsync(dto);
    return CreatedAtAction(nameof(GetById), new { id = created.Id }, value: created);
}
```

**What happens here:**
- ASP.NET Core receives the HTTP POST request
- Model binding deserializes the JSON body into `CreateEmployeeDto`
- Model validation runs (if you have `[ApiController]` and data annotations)
- The controller calls the service method
- The service returns an `EmployeeDto`
- The controller returns HTTP 201 Created with a Location header pointing to the new employee

**What the controller does NOT do:**
- It doesn't know about databases, EF Core, or persistence
- It doesn't enforce business rules (that's the service's job)
- It doesn't map entities to DTOs (that's the service's job)

The controller's only job is to handle HTTP: receive requests, call the service, return responses.

---

## Step 2 — The Service Orchestrates

The controller calls `EmployeeService.CreateEmployeeAsync`:

```csharp
public async Task<EmployeeDto> CreateEmployeeAsync(CreateEmployeeDto dto)
{
    var employee = new Employee
    {
        Name = dto.Name,
        Email = dto.Email,
        Salary = dto.Salary,
        DepartmentId = dto.DepartmentId
    };

    await _repository.AddAsync(employee);

    return new EmployeeDto
    {
        Id = employee.Id,
        Name = employee.Name,
        Email = employee.Email,
        Salary = employee.Salary,
        DepartmentId = employee.DepartmentId
    };
}
```

**What happens here:**
- The service creates an `Employee` entity from the input DTO
- The service calls the repository to persist the entity
- The repository returns the created entity (with `Id` generated by the database)
- The service maps the entity to an output DTO
- The service returns the DTO to the controller

**What the service does NOT do:**
- It doesn't know about HTTP (request, response, status codes)
- It doesn't know about EF Core (DbContext, SaveChanges)
- It doesn't know about database connections or transactions

The service orchestrates the use case: receive input, invoke domain logic, persist data, return output. It depends on abstractions (`IEmployeeRepository`), not implementations.

---

## Step 3 — The Repository Abstracts Data Access

The service calls `_employeeRepository.AddAsync`:

```csharp
public async Task AddAsync(Employee employee)
{
    _context.Employees.Add(employee);
    await _context.SaveChangesAsync();
}
```

**What happens here:**
- The repository adds the entity to EF Core's change tracker
- `SaveChangesAsync` persists the change to the database (this is the Unit of Work pattern)
- The database generates the `Id` (identity column)
- The repository returns the entity with the generated `Id`

**What the repository does:**
- Abstracts EF Core from the Application layer
- Implements the `IEmployeeRepository` interface defined in Application
- Handles persistence concerns (DbContext, SaveChanges)

**Why this matters:**
The Application layer (`EmployeeService`) depends on `IEmployeeRepository`, not `EmployeeRepository` or `AppDbContext`. If you switch from EF Core to Dapper or a NoSQL database, only the repository changes. The service doesn't know or care.

---

## Step 4 — Dependency Injection Wires It

In `Program.cs`:

```csharp
services.AddScoped<IEmployeeRepository, EmployeeRepository>();
services.AddScoped<IEmployeeService, EmployeeService>();
```

**What happens here:**
- Application defines interfaces: `IEmployeeRepository`, `IEmployeeService`
- Infrastructure provides implementations: `EmployeeRepository`, `EmployeeService`
- DI container connects them at runtime

When the controller requests `IEmployeeService`, DI provides `EmployeeService`.
When `EmployeeService` requests `IEmployeeRepository`, DI provides `EmployeeRepository`.

**This is Dependency Inversion in action:**
- High-level modules (Application) define abstractions
- Low-level modules (Infrastructure) implement them
- Both depend on abstractions, not on each other

The controller doesn't create `EmployeeService`. The service doesn't create `EmployeeRepository`. DI provides them. This makes the system loosely coupled and testable.

---

## Step 5 — DTOs Cross the Boundary

```
Controller                Service                   Repository
    |                        |                          |
    |-- CreateEmployeeDto -->|                          |
    |                        |-- Employee entity ------>|
    |                        |                          |
    |                        |<-- Employee entity ------|
    |<-- EmployeeDto --------|                          |
```

**In:** `CreateEmployeeDto` crosses from the API layer into the Application layer.
**Out:** `EmployeeDto` crosses from the Application layer back to the API layer.

**What stays inside the Application layer:**
- `Employee` entity (domain model)
- Business rules
- Mapping logic

**What crosses the boundary:**
- DTOs (input and output)

The domain entities never leave the Application layer. They're converted to DTOs before crossing the boundary. This protects the domain from external dependencies and allows the API to evolve independently.

## Step 6 — Identify the Patterns

| Pattern | Where You See It |
|---|---|
| **Dependency Inversion** | `IEmployeeRepository` defined in Application, implemented in Infrastructure |
| **Repository Pattern** | `EmployeeRepository` abstracts EF Core from the Application layer |
| **Unit of Work** | `DbContext.SaveChangesAsync` in `AddAsync` ensures atomic persistence |
| **Service/Use Case** | `EmployeeService.CreateEmployeeAsync` orchestrates the operation |
| **DTOs and Mapping** | `CreateEmployeeDto` in, `EmployeeDto` out, manual mapping in service |
| **CQRS (basic)** | `Get` methods (queries) vs `Create` method (command) |
| **Clean Architecture** | Domain at center, Application around it, Infrastructure on outside, API at edge |

Every pattern has a purpose. None are accidental. Together, they create a system that is:
- **Testable:** You can mock `IEmployeeRepository` to test the service
- **Maintainable:** Changes to EF Core don't affect the service
- **Flexible:** You can swap implementations without rewriting business logic
- **Clear:** Each layer has a single responsibility

## Step 7 — What Would You Change?

Think critically about the current architecture. There's no single right answer. The goal is to make deliberate choices based on the problem.

**Question 1: Should `SaveChangesAsync` move from repository to service?**

Currently, the repository calls `SaveChangesAsync`. Some argue the service should call it, making the repository a pure data accessor.

Arguments for moving it:
- The service orchestrates the use case, including persistence
- You can batch multiple repository calls in one transaction

Arguments against:
- The repository is responsible for persistence; saving is part of that
- The service shouldn't know about transaction boundaries

**Question 2: Should `Create` return `DepartmentName`?**

Currently, `Create` returns a DTO with `DepartmentName = null`. Should it re-query to populate it?

Arguments for re-querying:
- Consistent response: all `EmployeeDto` instances have `DepartmentName`

Arguments against:
- Extra database call for data the client can fetch if needed
- The client just created the employee; they know the `DepartmentId`

**Question 3: Is the repository adding value or just wrapping `DbSet`?**

`EmployeeRepository.AddAsync` is a thin wrapper around `DbSet.AddAsync` + `SaveChangesAsync`. Is this useful abstraction or unnecessary indirection?

Arguments for keeping it:
- It abstracts EF Core; you can switch to another ORM
- It provides a clean interface for testing

Arguments against:
- For simple CRUD, the repository adds little value
- EF Core's `DbSet` is already an abstraction

**Question 4: Would explicit use-case classes help here?**

Instead of `EmployeeService` with multiple methods, you could have `CreateEmployeeUseCase`, `GetEmployeeByIdQuery`, etc.

Arguments for:
- Each use case is isolated and focused
- Easier to add authorization, validation, logging per use case

Arguments against:
- Over-engineering for simple CRUD
- More files, more complexity, no clear benefit

## Step 8 — Verify the Architecture

Before claiming the architecture is correct, verify:

**Build succeeds:**
```bash
dotnet build
```

**No circular references:**
- Domain has no references to Application, Infrastructure, or API
- Application has no reference to Infrastructure
- Infrastructure references Domain and Application
- API references all layers (to wire up DI)

**Domain has no external dependencies:**
- No `Microsoft.EntityFrameworkCore` in Domain
- No `System.ComponentModel.DataAnnotations` (use domain-specific validation)

**Application doesn't reference Infrastructure:**
- `IEmployeeRepository` is in Application
- `EmployeeRepository` is in Infrastructure
- Application doesn't know about `AppDbContext`

**DI registrations are correct:**
```csharp
services.AddScoped<IEmployeeRepository, EmployeeRepository>();
services.AddScoped<IEmployeeService, EmployeeService>();
```

**Controller doesn't use `DbContext`:**
- Controller depends on `IEmployeeService`
- Controller doesn't depend on `IEmployeeRepository` or `AppDbContext`

If all these checks pass, the architecture is sound.

## Knowledge Check

**Question 1:** Trace the flow of data when creating an employee. What crosses layer boundaries, and what stays inside a layer?

<details>
<summary>Answer</summary>

`CreateEmployeeDto` crosses from API to Application. The service converts it to an `Employee` entity (stays in Application). The entity is passed to the repository, which persists it via EF Core (Infrastructure). The entity returns to the service, which converts it to `EmployeeDto`. `EmployeeDto` crosses from Application back to API. The `Employee` entity never leaves the Application layer.
</details>

**Question 2:** Why does the controller depend on `IEmployeeService` instead of `EmployeeService` directly? What would break if you changed it?

<details>
<summary>Answer</summary>

Depending on the abstraction (`IEmployeeService`) allows DI to provide the implementation. This makes the controller testable (you can mock the service) and flexible (you can swap implementations). If you depended on `EmployeeService` directly, you'd lose the ability to mock it in tests, and you'd create a tight coupling between the controller and a specific implementation.
</details>

**Question 3:** If you needed to switch from SQL Server to PostgreSQL, which layers would change? Which would stay the same?

<details>
<summary>Answer</summary>

Infrastructure would change: `EmployeeRepository` and `AppDbContext` would need PostgreSQL-specific configuration (connection string, possibly provider NuGet packages). Domain and Application would stay the same: entities, DTOs, service logic, and interfaces are database-agnostic. The API layer would stay the same: it only depends on `IEmployeeService`. You might need to update the connection string in `appsettings.json`, but no code changes in API.
</details>
