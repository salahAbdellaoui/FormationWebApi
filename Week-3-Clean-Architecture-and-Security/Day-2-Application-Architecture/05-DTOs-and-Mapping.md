# 05 — DTOs and Mapping

**Duration:** 25 minutes

---

## Why DTOs Exist

DTOs (Data Transfer Objects) separate the API contract from the domain model. They protect the domain from external changes and allow you to shape data for the client.

Without DTOs, your entities become your API. When your entity changes, your API changes. When your entity has navigation properties you don't want to expose, they get exposed. DTOs give you control.

---

## Our DTOs

```csharp
// Input DTO
public class CreateEmployeeDto
{
    public string Name { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
    public decimal Salary { get; set; }
    public int DepartmentId { get; set; }
}

// Output DTO
public class EmployeeDto
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
    public decimal Salary { get; set; }
    public int DepartmentId { get; set; }
    public string? DepartmentName { get; set; }
}
```

`CreateEmployeeDto` is for input — what the client sends when creating an employee.
`EmployeeDto` is for output — what the API returns when reading employee data.

They're different because the client doesn't send `Id` (generated by the database) or `DepartmentName` (looked up from the Department entity) when creating. The output DTO includes both because the API provides them.

---

## Why Not Return the Entity Directly?

If we returned `Employee` directly from our API:

- We'd expose the domain structure to the outside world. Any refactoring of `Employee` becomes a breaking API change.
- We can't control what data is sent. Navigation properties like `Department` would be serialized, potentially causing circular references or leaking internal structure.
- We can't add computed fields (like `DepartmentName`) without changing the entity, which pollutes the domain model with presentation concerns.
- We lose the ability to evolve the API independently of the domain. Different clients might need different shapes of data.

DTOs create a boundary. The domain model changes internally without affecting clients. Clients get exactly the data they need, shaped appropriately.

## Manual Mapping

In `EmployeeService`, we map entities to DTOs manually:

```csharp
private static EmployeeDto MapToDto(Employee employee)
{
    return new EmployeeDto
    {
        Id = employee.Id,
        Name = employee.Name,
        Email = employee.Email,
        Salary = employee.Salary,
        DepartmentId = employee.DepartmentId,
        DepartmentName = employee.Department?.Name
    };
}
```

This method is called by `GetAllEmployeesAsync` and `GetEmployeeByIdAsync`. The `Department?.Name` syntax safely handles cases where the Department navigation property might not be loaded.

In `CreateEmployeeAsync`, the mapping happens inline:

```csharp
return new EmployeeDto
{
    Id = employee.Id,
    Name = employee.Name,
    Email = employee.Email,
    Salary = employee.Salary,
    DepartmentId = employee.DepartmentId
};
```

Notice: `DepartmentName` is not set. It will be `null` in the response.

---

## The DepartmentName Issue

This is a real problem worth understanding.

**Get methods** use `Include(e => e.Department)` to load the Department navigation property. When `MapToDto` runs, `employee.Department?.Name` has a value, so `DepartmentName` is populated in the DTO.

**Create method** doesn't re-query after inserting. It receives `CreateEmployeeDto` with a `DepartmentId`, creates an `Employee` entity, saves it, and maps to DTO. The `Employee` entity doesn't have the Department loaded, so `DepartmentName` is null.

This is inconsistent: the same DTO (`EmployeeDto`) has different data depending on the operation. `GetById` returns a fully populated DTO. `Create` returns a DTO with null `DepartmentName`.

**Options:**

1. **Accept it:** Document that `Create` returns null `DepartmentName`. The client can fetch the full employee if needed. This is what we do in this teaching application.

2. **Re-query:** After `SaveChangesAsync`, load the employee again with `Include(e => e.Department)`. This guarantees consistency but adds an extra database call.

3. **Set manually:** If you know the department name, set it directly. But you don't have it — you only have `DepartmentId` from the input DTO. You'd need to query the Department first, which is also an extra database call.

4. **Use different response DTOs:** Create a `CreatedEmployeeDto` without `DepartmentName` for the Create response. This makes the inconsistency explicit but adds more DTOs.

For a real API, you might re-query or use different response DTOs. For this teaching application, accepting the inconsistency is appropriate. The goal is to understand the tradeoff, not eliminate it.

## Where Mapping Belongs

Mapping happens in the **Application layer** (`EmployeeService`).

- Not in the controller (controller doesn't know about entities)
- Not in the repository (repository returns entities, not DTOs)
- Not in the domain (domain has no knowledge of DTOs)

The service layer orchestrates: it receives DTOs from the controller, converts them to entities for the repository, receives entities back, converts them to DTOs, and returns to the controller.

---

## Mapping Libraries

Tools like AutoMapper, Mapster, and Mapperly reduce boilerplate by generating mapping code automatically.

```csharp
// AutoMapper example
CreateMap<Employee, EmployeeDto>();
var dto = _mapper.Map<EmployeeDto>(employee);
```

**Pros:**
- Less boilerplate code
- Automatic handling of property name matches
- Configuration in one place

**Cons:**
- Adds a dependency to your project
- Hides the mapping logic (what exactly is being mapped?)
- Reflection-based mapping can be slower (though some use source generators)
- Debugging mapping errors is harder
- For a few DTOs, the setup overhead exceeds the benefit

**When to use:**
- 50+ DTOs with complex mappings
- Team conventions require it
- Performance is not critical (or you use a source generator like Mapperly)

**When manual mapping is better:**
- Few DTOs (like this application)
- You want explicit, visible mapping logic
- You want to avoid dependencies
- Mapping includes custom logic or validation

For this application, manual mapping is appropriate. We have two DTOs and straightforward mappings. The code is clear, debuggable, and has zero dependencies.

## Common Mistakes

**Mistake 1: Returning entities directly**
```csharp
// Bad
public async Task<Employee> GetByIdAsync(int id)
```
This exposes your domain, leaks navigation properties, and makes your API fragile to domain changes.

**Mistake 2: Putting mapping in the controller**
```csharp
// Bad
public async Task<ActionResult<EmployeeDto>> GetById(int id)
{
    var employee = await _service.GetByIdAsync(id);
    return Ok(new EmployeeDto { Id = employee.Id, Name = employee.Name });
}
```
The controller shouldn't know about entity-to-DTO conversion. That's the service's job.

**Mistake 3: Creating DTOs that exactly mirror entities**
If your DTO has the same properties as your entity, ask why you have a DTO at all. DTOs should be shaped for the client's needs, not the domain's structure.

**Mistake 4: Using a mapping library for three DTOs**
Adding AutoMapper for two DTOs introduces a dependency, configuration, and indirection for no benefit. Manual mapping is clearer.

## Knowledge Check

**Question 1:** Why does `CreateEmployeeAsync` return a DTO with `DepartmentName = null` while `GetEmployeeByIdAsync` returns a DTO with `DepartmentName` populated?

<details>
<summary>Answer</summary>

`GetEmployeeByIdAsync` uses `Include(e => e.Department)` to load the Department navigation property, so `employee.Department?.Name` has a value. `CreateEmployeeAsync` doesn't re-query after inserting, so the Department is not loaded and `DepartmentName` remains null.
</details>

**Question 2:** Where should entity-to-DTO mapping happen, and why not in the controller?

<details>
<summary>Answer</summary>

Mapping belongs in the Application layer (service). The controller's job is to handle HTTP concerns (model binding, status codes). Mapping is a business concern — converting between domain and API contracts. Putting it in the controller mixes HTTP and business logic, violating separation of concerns.
</details>

**Question 3:** When would you choose a mapping library over manual mapping?

<details>
<summary>Answer</summary>

When you have many DTOs (50+) with repetitive mappings, when team conventions require it, or when mappings are complex enough that centralized configuration is clearer than scattered manual code. For a few DTOs with simple mappings, manual mapping is clearer, has no dependencies, and is easier to debug.
</details>
